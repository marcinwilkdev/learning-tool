# Ingest

You maintain a wiki that compounds: each new source enriches the existing pages
instead of producing a separate pile of notes. The web viewer and quiz generator
read everything from `kb/`. Paths are relative to the project root.

## Layout

```
kb/raw/<doc>.md          parsed PDFs, written by the script. Never edit, except to
                         transcribe scanned pages (step 1a).
kb/raw/<doc>.outline.md  reading plan, likely conversion losses and headings with line numbers
kb/manifest.json         documents, their wiki_built flag and scanned-page status
kb/sources/<doc>.md      one page per document: what it contains and where it was used
kb/concepts/<slug>.md    one page per concept, the core of the wiki
kb/topics/<slug>.md      learning units: ordered, scoped, reference concepts
kb/curriculum.json       modules and the learning order of their topics
kb/log.md                append-only record of every ingest
kb/site.json             optional site settings: {"lang": "pl"} sets the interface language
kb/index.json            generated by learnkb-check. Never edit.
```

**Language.** The wiki is in English unless the user asks for another language (for example
"po polsku"). Then write titles, definitions and body text in that language, and set
`kb/site.json` to `{"lang": "<code>"}` so the site's interface matches (supported: en, pl;
others fall back to English). Keep the section headings (`## Overview`, `## Explanation`…),
the `> Note:` callout label and the frontmatter keys in English: the scripts find sections
by those names, and the site shows them translated. Slugs stay ASCII (`lozysko`, not `łożysko`).

Slugs are lowercase-kebab and **unique across the whole wiki**. Link pages with
`[[slug]]` or `[[slug|display text]]` (Obsidian-compatible).

## Progress
The user may be watching the build on the admin panel (`uv run learnkb-serve`, at /admin/). Report
each step as you start it, so the panel shows where you are:

```bash
uv run learnkb-admin step read "Part 3: Working with Remotes" --doc <doc> --part 3
```

Phases, in order: `parse` (logged by `learnkb-ingest` itself), `transcribe` (scanned
documents only, step 1a, with `--doc`), `read` (once per
reading-plan part, with `--doc` and `--part`), `source`, `concepts`, `topics`,
`curriculum`, `check`, and `done` when you've finished. The message is optional and short.
If you deliberately leave parts of the reading plan unread (a book's index, say), log them
once with `--skip` so the panel shows them as skipped and leaves them out of its coverage
figure: `uv run learnkb-admin step read "Index" --doc <doc> --part 25-30 --skip`.
One call per step is enough. Don't log every file: the panel sees file writes by itself.

## Procedure

### 1. Parse
Run `uv run learnkb-ingest`. Documents with `"wiki_built": false` in the manifest
are pending. If none are pending and the user didn't ask for a rebuild, stop.

### 1a. Transcribe scanned pages
A page without a text layer (a scan, a photo, handwritten notes) only gets OCR, which
reads print well but garbles handwriting, and its confidence score doesn't notice. The
script lists such documents as "awaiting transcription check" and gives them
`"transcription": "pending"` and `scanned_pages` in the manifest. For each one:

1. **Judge the draft.** `Read` the PDF with `pages` set to one or two scanned pages and
   compare them with the same pages in `kb/raw/<doc>.md` (each page starts at a
   `<!-- page N -->` marker). If the draft says what the page says, with only the odd
   typo, keep it: `uv run learnkb-ingest --ocr-ok <doc>`, and go on to step 2.
2. **Otherwise transcribe.** Log `uv run learnkb-admin step transcribe "Pages 1–20" --doc <doc>`
   for each batch. `Read` the PDF at most 20 pages per call and write what each page
   says into `kb/raw/<doc>.md`, replacing that page's OCR text between its marker and
   the next. Keep the markers. Text pages of a mixed document stay as they are. Rules:
   - Transcribe; don't edit. Keep the source's language, wording, abbreviations and
     numbers, even ones that look wrong. Never fill a gap from your own knowledge.
   - Structure it as Markdown: a heading the page shows becomes `## Heading` (in
     normal sentence case if the page writes it in capitals), bullets become lists,
     arrows and nesting become nested lists, tables become tables.
   - Text in the margin or in another colour goes next to what it annotates.
   - A drawing or picture becomes one comment describing only what is visible,
     labels included: `<!-- figure: two columns of four cervix drawings, labelled ... -->`.
   - Mark what you can't read `[illegible]` and an uncertain reading `[word?]`. Leave
     out crossed-out text.
3. **Long documents.** More than about 40 scanned pages: hand batches of 10–20 pages to
   subagents in parallel, each with the rules above, the PDF path and its page range,
   and each writing its pages to a file in your scratchpad. Then put them into
   `kb/raw/<doc>.md` in page order yourself.
4. **Finish.** `uv run learnkb-ingest --transcribed <doc>` records it and rebuilds the
   outline. Read the new outline before step 3: its headings are what pages will cite.

### 2. Get your bearings
Read `kb/index.json` if it exists. It lists every page with its title, definition
or summary, and links. This tells you what the wiki already knows, so you can
merge into it instead of duplicating.

### 3. Process one document at a time
For each pending document, read `kb/raw/<doc>.outline.md` first. Then read
`kb/raw/<doc>.md` in full, one part of its reading plan per `Read` call (offset and
limit as listed), noting section headings for citations. Where the outline flags a
possible conversion loss, look at those lines: a command or output that became an
image is gone, so don't reconstruct it from outside knowledge. Use what the
surrounding text states, or leave it out. Then:

1. **Source page**: write `kb/sources/<doc>.md`.
2. **Concepts**: list the concepts the document teaches. For each one:
   - **Already in the wiki** (check titles *and* `aliases`): read the page and
     integrate the new material. Add detail, examples or a new perspective;
     append to `sources`; don't just tack a paragraph on the end. If this source
     contradicts the page, keep both views in a `## Source disagreements`
     section, attributed to each source.
   - **New**: create the page.
   - Skip trivia. A concept deserves a page if a learner would need to look it
     up or a quiz could reasonably ask about it.
3. **Topics**: decide which topics this document's concepts belong to. Extend
   existing topics, or propose new ones. A topic is one learnable unit (about
   15–45 minutes) and may draw on several documents.
4. Set `"wiki_built": true` for the document in the manifest.

**Outline:** don't stop for approval. Write the topic pages straight away, and on the
first ingest, or whenever you add or restructure modules, put the outline
(modules → topics → key concepts) in the report so the user can ask for changes
afterwards.

### 4. Curriculum and log
Update `kb/curriculum.json` so every topic sits in exactly one module, ordered
prerequisites-first. Append an entry to `kb/log.md`.

### 5. Check
Run `uv run learnkb-check`. Fix every ERROR, and fix warnings where reasonable
(orphan concepts usually mean a topic or related concept should link to them).
Repeat until it passes. Passing regenerates `kb/index.json`.

### 6. Report
Summarise for the user:
- documents processed
- concepts created or updated
- topics created or updated
- the outline (modules → topics → key concepts), on the first ingest or when modules
  changed, and that the user can ask to merge, split, rename or reorder topics
- any contradictions you found
- any badly parsed content in `kb/raw/`, such as garbled tables or OCR noise, starting
  from the outline's *Possible conversion losses*
- scanned documents: whether you kept the OCR or transcribed them, and any `[illegible]`
  passages

## Page formats

Content rules for every page:
- Write only what the sources support. Never fill gaps with outside knowledge.
  When something is clearly missing, say so in a `> Note:` callout.
- Write in your own clear words. Quote briefly only when the exact wording
  matters, such as a formal definition.
- `sources` entries are `{doc: <doc-slug>, section: "<heading in raw>"}`. The section must
  match a heading in `kb/raw/<doc>.md` (case and spacing aside); `learnkb-check` warns
  when it doesn't.
- Frontmatter is YAML: in flow lists and maps, double-quote any value containing `@`, `{`,
  `}`, `?`, `:` or a comma, e.g. `aliases: [git reflog, "HEAD@{n}", "@mentions"]`.
- Close every link: `[[slug]]` or `[[slug|Label]]`. `learnkb-check` reports unclosed and
  broken links in pages, lessons and quizzes.

### Source: `kb/sources/<doc>.md`
```markdown
---
type: source
title: Attention Is All You Need
doc: attention            # manifest slug (same as this file's slug)
authors: [Vaswani et al.]
year: 2017
---
## Summary
What the document is about and who it's for, in 3–6 sentences.

## Contents
- **3.2 Attention**: introduces [[scaled-dot-product-attention]] and [[multi-head-attention]].

## Parsing notes
Pages or tables that converted badly (omit if none).
```
This page's slug is the doc slug. It doesn't conflict with concepts because doc
slugs are file names. If a concept would need the same slug, give the concept a
more specific one.

### Concept: `kb/concepts/<slug>.md`
```markdown
---
type: concept
title: Scaled dot-product attention
aliases: [dot-product attention]
definition: One sentence a learner could memorise.
related: [multi-head-attention, softmax]
sources:
  - {doc: attention, section: "3.2.1 Scaled Dot-Product Attention"}
---
## Explanation
Intuition first, then the precise version (formulas, mechanics).

## Example
A worked example from the sources, where they give one.

## Related
How it connects: builds on [[softmax]], used inside [[multi-head-attention]].
```

### Topic: `kb/topics/<slug>.md`
```markdown
---
type: topic
title: How attention works
module: transformer-architecture
summary: One or two sentences.
difficulty: beginner        # beginner | intermediate | advanced
prerequisites: [vector-basics]          # topic slugs
concepts: [scaled-dot-product-attention, multi-head-attention]
sources:
  - {doc: attention, section: "3.2 Attention"}
---
## Learning objectives
- Explain why attention scales by √d_k.
(Concrete, testable outcomes. The quiz generator writes questions against these.)

## Overview
Why this matters and how the pieces fit together.

## Walkthrough
The narrative path through the material. Link every concept on first mention
([[scaled-dot-product-attention]]) and don't repeat the concept pages in full.
The topic tells the story; the concept pages hold the details.

## Common pitfalls
Misconceptions the sources warn about or that the material invites.

## Summary
3–5 takeaways.
```

### `kb/curriculum.json`
```json
{"modules": [
  {"slug": "transformer-architecture", "title": "Transformer architecture",
   "summary": "One sentence.", "topics": ["vector-basics", "how-attention-works"]}
]}
```
List modules in learning order. Module slugs are only used here and in topic
`module` fields.

## 2026-10-15 ingest: Attention Is All You Need
